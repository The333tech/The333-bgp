# Security Policy

## Поддерживаемая версия

| Версия | Security-исправления |
|---|---|
| **v0.82.1b (beta)** | поддерживается |
| v0.82b и более ранние | не поддерживаются |

Обновись до поддерживаемой версии перед отправкой отчёта, если проблема не относится непосредственно к процессу обновления.

## Сообщить об уязвимости

**Не публикуй описание уязвимости, exploit, секреты или внутренние данные в обычном GitHub Issue.**

Используй [Private vulnerability reporting](https://github.com/The333tech/The333-bgp/security/advisories/new). Если кнопка приватного отчёта недоступна, создай Issue без технических подробностей и запроси приватный канал связи.

В приватном отчёте укажи:

- версию The333-BGP, ОС VM, версию Docker и RouterOS;
- затронутый компонент и ожидаемое влияние;
- минимальные шаги воспроизведения;
- безопасный proof of concept без реальных паролей, токенов, ключей и приватных адресов;
- известный способ временно снизить риск, если он есть.

Отчёт будет проверен до публичного обсуждения. Срок исправления зависит от серьёзности и воспроизводимости проблемы; фиксированный SLA для beta-версии не заявляется.

## Базовая модель безопасности

The333-BGP рассчитан на запуск в доверенной локальной сети рядом с MikroTik.

**Не открывай порты `8090`, `8088` и `179` напрямую в Интернет.**

Для доступа извне используй один из вариантов:

- VPN до локальной сети;
- reverse proxy с TLS;
- firewall allowlist по IP.

## Пароль портала

- Страница входа запрашивает только пароль; внутренняя учётная запись `admin` фиксирована и не вводится пользователем.
- Минимальная длина пароля: 8 символов.
- Новые установки хранят пароль как `WEB_PASSWORD_HASH` с PBKDF2-HMAC-SHA256 и 600 000 итераций.
- Пароль передаётся только при входе и не сохраняется в браузерном Web Storage.
- После входа backend выдаёт ограниченную по времени `HttpOnly`, `SameSite=Strict` session cookie; для изменяющих запросов требуется отдельный CSRF-токен.
- Перезагрузка страницы восстанавливает действующую сессию без повторной передачи пароля. Выход из портала немедленно инвалидирует сессию.
- Backend ограничивает количество неудачных попыток входа.

## TLS портала

Локальная установка по умолчанию использует HTTP и предназначена только для доверенной LAN/VPN. Для включения HTTPS:

```bash
cd /opt/the333-bgp
./scripts/the333bgp.sh tls-enable /путь/к/portal.crt /путь/к/portal.key
```

Команда принимает PEM certificate chain и незашифрованный PEM private key, проверяет их совпадение и сохраняет в root-only `/etc/the333-bgp/tls`. Private key не находится в проекте и не попадает в system backup портала. TLS-режим включает `Secure` для session cookie и оставляет тот же порт `8090`.

Отключение TLS:

```bash
./scripts/the333bgp.sh tls-disable
```

Смена пароля на VM:

```bash
cd /opt/the333-bgp
./scripts/the333bgp.sh set-password
```

## API

Все информационные и управляющие API требуют авторизацию портала. Публичны только `/health` и ручки входа/проверки сессии; `/health` используется healthcheck'ом контейнера и не возвращает секреты. Legacy Basic Auth выключен по умолчанию (`AUTH_ALLOW_BASIC=false`).

## MikroTik

- Перед изменением BGP создай зашифрованный RouterOS backup и скачай его с устройства.
- Обеспечь независимый доступ через MAC WinBox, serial console или физический доступ.
- Не вставляй в Portal `/export show-sensitive`, AWG private keys, preshared keys и пароли.
- Помощник сначала создаёт выключенное BGP connection с quarantine filter. Активация выполняется отдельным этапом после проверки.
- Не применяй RouterOS 7 команды к RouterOS 6.
- Не загружай container image по mutable-тегу `latest` без проверки конкретного release и SHA-256/digest.

## Обновления

Обновления запускаются через host-side systemd service `the333-bgp-updater.service`. Его API слушает только Unix socket `/run/the333-bgp/updater.sock`, требует отдельный случайный token и принимает только фиксированную операцию update с валидированными channel/version.

Docker socket **не монтируется ни в один контейнер**. Backend видит только каталог с Unix socket updater. Сам systemd service имеет необходимые права на Docker host, поэтому доступ к VM, `.env`, unit-файлу и updater token нужно защищать как административный.

Перед заменой файлов Backend кратко приостанавливается для согласованной резервной копии и обязательно запускается снова; GoBGP при этом не останавливается. После перезапуска проверяется готовность backend, GoBGP и портала; при ошибке обновлятор автоматически возвращает файлы предыдущей версии.

Release archive проверяется по обязательному `sha256` до распаковки. Не меняй manifest URL на неизвестный источник.

## Автоматические проверки

- CI, Release и сборка `docker-awg` используют закреплённую версию Grype и блокируют известные исправимые уязвимости уровня High/Critical.
- Python- и npm-зависимости проверяются отдельными dependency audit; CodeQL анализирует Python и JavaScript/TypeScript.
- GoBGP собирается из точного upstream commit, транзитивные Go-модули закреплены и проходят `go mod verify`.
- Любое исключение scanner хранится в `.grype.yaml`, ограничивается конкретными CVE, пакетом и версией и сопровождается проверяемым обоснованием. Широкие или бессрочные маски не используются.

Текущее узкое исключение относится к `CVE-2026-15308` в CPython `3.14.6`: уязвимость находится в `html.parser`, который backend не импортирует и не вызывает. Переход production runtime на ещё не стабильную ветку Python 3.15 не выполняется; исключение пересматривается при каждом обновлении Python.

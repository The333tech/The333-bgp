# Участие в разработке The333-BGP

Спасибо за желание улучшить проект. Небольшие, проверяемые изменения с понятным влиянием на маршрутизацию рассматриваются быстрее больших несвязанных наборов правок.

## Перед началом

- Проверь существующие Issues и Pull Requests, чтобы не создавать дубликат.
- Для ошибки используй форму **Сообщить об ошибке**, для новой возможности — **Предложить улучшение**.
- Уязвимости отправляй только по приватному процессу из [SECURITY.md](SECURITY.md).
- Для крупного изменения сначала создай Issue и согласуй ожидаемое поведение.

## Требования к изменениям

- Создавай отдельную ветку от актуальной `main`.
- Не смешивай функциональную правку с несвязанным рефакторингом или форматированием.
- Сохраняй пользовательские `.env`, `data/` и `config/` при установке и обновлении.
- Явно учитывай влияние на BGP-сессию и непрерывность публикации маршрутов.
- Не добавляй пароли, токены, private keys, реальные конфигурации RouterOS, runtime-данные, логи или backup-архивы.
- Новое поведение покрывай тестом на успешный и ошибочный сценарии.

## Проверка

Перед Pull Request выполни проверки, относящиеся к изменению:

```bash
./scripts/release-check.sh
python3 -m unittest discover -s tests -v
```

Для портала:

```bash
cd portal
npm ci
npm test
npm run build
npm audit --omit=dev --audit-level=moderate
npm audit --audit-level=high
```

Для Docker, установщика или runtime дополнительно проверь Compose-конфигурацию и сборку затронутых образов. Не выполняй тестовое применение маршрутов на рабочем роутере без backup, Safe Mode и независимого доступа к MikroTik.

Для изменения ротации есть отдельная Linux-проверка на **локальном тестовом Docker**, не на рабочей VM:

```bash
THE333_ALLOW_LOCAL_DOCKER_TEST=YES python3 tests/storage_docker_smoke.py
```

Она импортирует маленькие временные образы без загрузки из реестра, создаёт только остановленный контейнер с уникальным именем, проверяет защиту его образа и чужой метки, затем удаляет только свои тестовые ресурсы. Два комплекта отката остаются проверяемыми. Общий `prune` не используется. Обычный `unittest discover` этот тест с реальным Docker не запускает.

### Испытания поставки

CI собирает и запускает основные образы на **нативных** `ubuntu-24.04` (amd64) и `ubuntu-24.04-arm` (arm64), без подмены запуска эмуляцией. Полный prebuilt-стенд вызывается reusable workflow `delivery.yml`: для кандидата после opt-in сборки GHCR, для релиза — после упаковки архива, **до создания GitHub Release**. Контроль установки уже опубликованного архива остаётся отдельной проверкой обеих архитектур.

Метка `build-ghcr-candidate` в PR из этого же репозитория включает существующую публикацию только `candidate-<commit>` образов. После сборки и сканирования стенд проверяет чистую установку, переход с опубликованной `0.92b`, сохранение сессии/настроек/маршрутов/паузы BGP, восстановление ZIP, ошибки диска/SHA-256/GHCR и настоящий откат после ошибки запуска OCI. Для повторных операций используются временные номера `9000.*b` **только на стенде**, не теги и не версии продукта.

`tests/delivery_smoke.py` допускается **только на свежей GitHub-hosted Linux VM**. Не запускайте его на рабочем сервере: он использует стандартные контейнеры/порты и systemd unit проекта. Защитные проверки отказывают при существующей установке или контейнерах. Только свои тестовые файлы, сертификат и runtime удаляются при завершении; общий Docker prune не применяется. Приватный ключ тестового HTTPS-сервера не входит в публикуемые отчёты.

Обновление тестируется через настоящий Unix API host-updater с разрывом соединения клиента; аутентификация и остальные операции — через HTTP API портала. Загрузка списка релизов Backend и браузерный сценарий отдельно покрыты тестами Backend/Playwright: локальный HTTPS fixture намеренно не обходит SSRF-защиту Backend. Внешний MikroTik, реальный VPN-путь, полностью новая ОС без Docker и произвольные топологии этим стендом не проверяются. Подробные JSON-результаты CI содержат только архитектуру и названия пройденных этапов, не `.env` или журналы с настройками.

## Pull Request

В описании укажи:

- что изменено и какую проблему решает;
- как проверено поведение;
- меняется ли формат данных или `.env`;
- перезапускается ли `the333-gobgp-core`;
- ожидается ли временный отзыв маршрутов;
- как откатить изменение при неудаче.

Pull Request должен проходить CI, CodeQL и dependency checks. Обновление зависимости не принимается только ради номера версии: должна быть понятна совместимость, польза или закрываемый риск.

## Выпуски

- Промежуточные изменения проверяются через Pull Request и CI без отдельного тега.
- Тег создаётся для версии, готовой к установке, либо для необходимого исправления уже опубликованного выпуска после успешных проверок Pull Request. Release workflow проверяет тег перед публикацией файлов GitHub Release.
- Опубликованные теги не переписываются и не удаляются ради сокращения списка: они сохраняют воспроизводимость выпущенных архивов. Актуальная политика поддержки указана в [SECURITY.md](SECURITY.md).
